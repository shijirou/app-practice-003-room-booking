# 画面デザイン

[要件定義書](requirements.md) の「画面」の詳細。**見た目の最終形は [mock/index.html](mock/index.html)（ブラウザで開く。DB・API なし。リロードすると元に戻る）**。この文書は、モックの内容を言葉にした「要素の一覧」と、実装の手順を決めたもの。
画面は 1 つだけ。パソコン（幅 1024px 以上）を想定。

> **この文書は最終モックに合わせて書き直した**（Issue #50）。以前は初期案（予約フォームが下にある形）のまま古くなっていて、縦切り 1 の最初の実装がその初期案に引きずられた。モックを変えたら、同じ PR でこの文書も直す。

## 完成デザイン（文字と線の図）

```
┌─────────────────────────────────────────────────────────────────────┐
│ 会議室予約表                               ログイン中（仮）[田中架空 ▼]  │
├─────────────────────────────────────────────────────────────────────┤
│ [◀][今日][▶] [ 2026年11月20日（金） 📅 ] [現在 10:15]                   │
│ 空き枠を押して予約（ドラッグで長い時間も）。8:00〜20:00・30 分刻み。  （？）│
│ 会議室     │ 8:00 │ 9:00 │ 10:00 │ 11:00 │ ... │ 19:00 │       20:00 │
│ 会議室A(4名)│ 空き  │営業定例（佐藤）│ 空き ┃ ...   ← 縦線（1 時間ごと太く）│
│ 会議室B(6名)│ 空き（行は 1 行おきに薄いグレー）  │ 商談（田中）← 自分は青   │
│ 会議室C(10名)│ ...                       赤い縦線 = 現在時刻            │
│ 商談ブース(2名)│ ...                                                  │
│ （空き枠を押す・ドラッグすると、その場にポップアップで予約）               │
├─────────────────────────────────────────────────────────────────────┤
│ [自分（田中架空）の予約 3件] [11/20(金) の予約（みんな）5件]  ← タブ  │
│ ┌ 11/20(金) 10:00〜11:00  会議室B ／ 営業定例     [変更] [キャンセル] ┐  │
│ └ 11/22(日) 14:00〜15:30  商談ブース ／ オンライン商談 [変更] [キャンセル]┘ │
└─────────────────────────────────────────────────────────────────────┘
```
- 表の列は 30 分ごと（8:00〜20:00）。予約済みのマスは予約の長さに合わせてつながり、「用件（名前。「架空」は省く）」を出す。
- 自分の予約は青、ほかの人の予約はグレー、空きは白、過去の時間は斜線。
- 下の「自分の予約」「みんなの予約」の切り替えは、ファイルの見出し風のタブ。
- 予約・変更は、表の枠の近くに出る**ポップアップ**で行う（下にフォームは置かない）。

## 実装の手順（画面を作る縦切りは必ず守る）
1. **計画の前に、モックの該当部分を全部読む**。名前だけ拾わない。`<style>` と、その縦切りに関わる `<script>` の関数を読む。
2. **計画に「入れる要素」と「入れない要素」を表で出し、ユーザーの了承を取る**。上の「要素の一覧」から、その縦切りの行を全部出す。落とす行があれば理由を書く。
3. **見た目は、モックの CSS を移す**。必要な部分を自分の判断で減らさない。
4. **終わる前に、要素の一覧と 1 行ずつ見比べる**。画面の見た目は、AI が見えない場合があるので、ユーザーにモックと並べて見てもらう。
5. **モックを直したら、同じ PR でこの文書も直す**。「完成」と言う前に、状況の列を更新する。

## モックの扱い（今後のアプリにも使う方針）
- モックは**最小限**にする（画面の流れ・配置・主な色まで）。細かい見た目（縦線・時計・カレンダーなど）は、本物のアプリの画面で作りながら仕上げる。
- 理由: モックは使い捨てなので、磨くほど「本物に移す」手間が増え、移し忘れ（今回の食い違い）の原因になる。
- この app-practice-003 では、モックを先に作り込んだので、上の「要素の一覧」と「実装の手順」で、移し忘れを防ぐ。

> **注意（次のアプリのモックを直すときに必ず読む）: モックは「お客様が合意できる最小の細かさ」で止める。こだわりすぎない。見た目を磨くのは、動く本物でする。**

### モックの目的は 3 つの合意
1. 流れ（誰がどの順で操作するか） 2. 中身（必要な情報・ボタンが足りているか） 3. 雰囲気（色や文字がイメージと大きく違わないか）。3 つが取れたら、そこで止める。

### 直すかどうかの 3 つの質問
一人開発では persona の視点で気になる点がいくらでも出るので、次で振り分ける。

| 質問 | 扱い |
|---|---|
| 1. 要件の機能・流れ・必要な情報が変わる（足りない・余分・手順の誤り） | **モックで直す** |
| 2. 色・余白・文字の大きさ・文言・動きなど見た目の細かさ | **本物で直す**（モックは直さない） |
| 3. あったら嬉しい程度の工夫 | **やらない**。後回しの記録に 1 行だけ書く |

目安は「これが無くても、要件の機能は全部できるか」。できるなら工夫なので、モックでは直さない。

### 止めるための仕組み
- モックの修正は 2 回まで（3 回目からは本物で直す）。1 回の修正は 30 分まで。
- 直す前に「persona の〇〇が△△で困るから」と 1 行で理由を書く。書けない修正は、質問 2 か 3。
- 色・余白・文字の大きさは、最初から共通の値（CSS 変数）にして、モックから本物へ機械的に移せるようにする。
