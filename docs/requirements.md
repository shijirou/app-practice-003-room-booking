## 1. 目的
社員が PC から、会議室の空き状況を確認して予約・変更・キャンセルできるようにする。
同じ会議室・同じ時間帯の予約の重複をなくし、総務部の負担を減らす。

## 2. 決定事項（未確認だった点）
クライアントに確認できないため、次の案で進める。変更があれば、このファイルを直す。

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | ログイン | なし。画面の上部で社員を選ぶ（パスワードなし） | 学習用で、本物の認証は範囲外。社員が約 6 名なので、プルダウンで選べる（多いと使いにくくなるため、クライアントの規模を小さくした） |
| 2 | 社員データ | 架空の 6 人を DB に最初から入れる（社員の追加は決定事項 10 を参照） | 実在の個人情報を使わない。プルダウンが長くなりすぎない人数にする |
| 3 | 会議室データ | DB に最初から入れる（管理画面なし） | 管理者画面は作らない |
| 4 | 重複の防止 | Java 側のチェック + DB 側の制約（PostgreSQL の排他制約）の二重で守る | 同時に押されても重ならないようにする（最重視） |
| 5 | 時刻の入力 | 30 分刻みの選択式。終了が開始より前（同じも不可）は受け付けない | 日時の入力間違いを防ぐ |
| 6 | 空き状況の見せ方 | 「会議室 × 時間」の表 | 一目で空きが分かる |
| 7 | 変更・キャンセル | 予約した本人（画面で選んだ社員）の予約が対象 | 他人の予約を誤って消さない |
| 8 | 予約できる時間帯 | 8:00〜20:00、同じ日の中。過去の日時は予約・変更できない | 日時の間違いを防ぐ。**確定** |
| 9 | 用件 | 予約に任意の「用件」（50 文字まで）を付けられる | 表で、何の予約か分かる。**確定** |
| 10 | 社員の追加機能 | 他が済んだ最後に作るか相談する（作るなら、名前の追加だけ・同じ名前は不可） | 優先度が低い |
| 11 | 予約できる先の期間 | 今日から 90 日先まで | 遠い先の予約で枠を押さえ続けない。**確定** |
| 12 | 1 件の最長時間 | 4 時間まで | 1 人が長く占有しない。**確定** |
| 13 | 土日・祝日 | 予約できる（祝日の判定は作らない） | 機能を増やさない。**確定** |
| 14 | 始まった予約 | 開始前だけ変更・キャンセルできる | 過去の記録を書き換えない。**確定** |
| 15 | ほかの人の予約の見え方 | 用件と社員名が見える（変更・キャンセルは本人だけ） | 誰に聞けばよいか分かる。**確定** |
| 16 | 社員の削除（将来） | 予約があるときは削除できない（作る場合） | 予約の持ち主が消えるのを防ぐ。**確定** |
| 17 | 自分の予約どうしの重なり | 同じ社員が、同じ時間帯に、**別の会議室**を予約することは禁止しない。画面で警告（小窓の黄色い注意文）と確認（「重ねて予約しますか？」）を出す。API は止めない。同じ会議室の重複は、これまでどおり禁止 | 同時に押さえる使い方がありうる一方、うっかりのダブルブッキングは防ぎたい。**確定**（2026-11-24） |

## 3. 機能要件
| ID | 機能 | 内容 | 元の希望 |
|---|---|---|---|
| F1 | 社員の選択 | 画面上部で、操作する社員を選ぶ | （ログインの代わり） |
| F2 | 会議室一覧・空き状況 | 日付を選ぶと、「会議室 × 時間」の表で予約済み・空きが分かる | 1 |
| F3 | 予約 | 会議室・日付・開始・終了（30 分刻み）を選んで予約する。重複・不正な時間はエラーにする | 2, 3, 6 |
| F4 | 予約の確認・変更 | 自分の予約を一覧で確認し、会議室・日時を変更できる。変更でも重複は許さない | 4 |
| F5 | キャンセル | 自分の予約を、確認メッセージのあと取り消す | 5 |

## 4. 非機能要件
| 項目 | 内容 |
|---|---|
| 対応機器・ブラウザ | PC の Chrome・Edge の最新版（画面幅 1024px 以上を想定）。スマートフォン向けの最適化はしない |
| 操作のしやすさ | 説明なしで使える。日時は選択式で、入力間違いが起きにくい |
| 性能 | 約 6 人が使う前提。画面の表示・予約・変更・キャンセルの結果が、1 秒以内に出る |
| 同時操作 | 2 人が同じ枠を同時に押しても、片方だけ成功し、もう片方は分かりやすいエラーになる（DB の排他制約で保証） |
| アクセシビリティ | キーボードだけでも操作できる。色だけに頼らず、予約済みのマスには文字も出す。エラーは文字で伝える |
| 日時 | 日本時間（Asia/Tokyo）に固定する。サマータイムは考えない |
| データの扱い | 過去の予約も消さずに残す。バックアップ・復旧は対象外（学習用）。DB のデータは Docker のボリュームに残る |
| 安全性（個人情報） | 実在の個人情報を入れない（社員・会議室・用件は架空）。ログに個人情報や用件の中身を出さない |
| 安全性（なりすまし） | ログインがないため、**誰でも他の社員になれる**（既知の制約）。外部には公開せず、自分の PC 内だけで動かす。本物の認証は対象外 |
| 安全性（入力） | 入力の検証は画面と API の両方で行う。SQL は値をパラメータで渡す。画面は入力文字をそのまま HTML にしない（React の標準のエスケープに任せ、`dangerouslySetInnerHTML` は使わない）。CORS は許可しない（画面は Vite の中継経由で、ブラウザから見て同じ場所（5173）から API を呼ぶので、許可が要らない）。エラーに内部の詳細を出さない |
| 秘密情報 | DB のパスワードなどは `.env` に書き、GitHub に載せない（公開リポジトリ）。見本は `.env.example` |
| 依存部品の安全 | Dependabot のアラートを確認し、重大なものは直す |
| 品質 | 型チェック・lint・テスト・E2E テストを CI で動かす。網羅率は測るだけ |
| 保守性 | 画面・API・DB を分ける。DB の変更は Flyway の SQL で履歴を残す。設計書（docs/）はコードと同時に更新する |

## 6. 対象外（最初は作らない）
- 繰り返し予約
- メール通知
- 管理者画面（会議室の追加・削除）
- 本物のログイン
- スマートフォン・タブレット向けの最適化

## 7. リスクと対策
| リスク | 影響 | 対策 |
|---|---|---|
| 同時に同じ枠を予約される | 予約の重複（最重視） | Java のチェック + DB の排他制約。同時実行のテストを書く |
| なりすまし（ログインなし） | 他人の予約を変更・取り消せる | 学習用の既知の制約として明記。外部に公開しない。本人の予約だけ変更できる（API でも確認） |
| 公開リポジトリへの情報の混入 | 秘密情報・個人情報の漏えい | `.env` を Git に入れない。架空のデータだけ使う。公開前の安全確認を行う |
| 日時の入力間違い・時差のずれ | 違う時間に予約される | 選択式・日本時間に固定・画面と API の両方で検証 |
| 部品の脆弱性 | 攻撃を受けやすくなる | Dependabot を確認し、安定版の最新を使う |
| 仕様の食い違い（設計書と実装） | 作り直し | 設計書をコードと同時に更新し、モックと見比べる |

## 8. 完成の目安
- F1〜F5 が動く。
- 同じ会議室・同じ時間帯の予約が、どんな操作でも重ならない（同時操作でも）。
- 実在の個人情報・秘密情報がどこにも入っていない。
