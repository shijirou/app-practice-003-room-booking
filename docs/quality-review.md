## 2026-11-25 公開前の総合監査で見送りにした項目
監査（調査のみ）の指摘のうち 7 件は直した（#177・#179・#181・#183・#185）。残りは、次の理由で見送った。理由は 2026-11-26 にコードを確かめて書いた（#188）。前提は「自分のパソコンだけで動かす学習用で、社員約 6 名の規模」。

| 項目 | 今の状態 | 見送る理由 | 直すきっかけ |
|---|---|---|---|
| 大きいコンポーネントの分割 | `App()` と `Timetable()` が、それぞれ約 400 行 | 動きは変わらず、分け方を誤ると不具合が入る。機能を増やす予定がない | 機能を足す・同じ所を何度も直すようになったら |
| 検査が画面と API の 2 か所にある | 画面は `validate.ts`、API は `ReservationRules`。同じ決まりを両方に書いている | 画面は送る前にすぐ知らせるため、API は必ず守るためで、両方に役割がある。まとめるには仕組みが増える | 決まりを変えるときは両方を直す。ずれが起きたら見直す |
| 同じ予約を同時に変更した場合 | 楽観ロック（版の番号）がなく、後から届いた変更が勝つ。専用のテストもない。別の予約との重なりは、DB の制約 `no_overlap` が防ぐ | 変更できるのは本人だけなので、起きるのは本人が 2 つの画面で操作したときくらい | 本人以外（管理者など）も変更できるようにするとき |
| `start_at` だけの索引がない | 日付での検索に使える専用の索引はない（索引は社員 + 開始時刻と、会議室の重なり用） | 予約の件数が少なく、困らない見込み（速さは測っていない） | 件数が増えて、日付の表示が遅くなったら |
| CSS とテストが 1 ファイルで大きい | `App.css` は約 1000 行、`App.test.tsx` は約 1700 行 | 読みやすさの問題で、動きには影響しない | コンポーネントを分けるときに、一緒に分ける |
| favicon が空 | `index.html` で `data:,`（空）を指定している | 機能に影響しない | 画面の写真を撮る前に、見た目を整えたくなったら |
| 色のコントラストが低い所 | カレンダーの「ほかの月の日付」（透明度 0.4）と、非活性のボタン（透明度 0.6）。監査の比は約 2.4 と 2.8 だが、推測値で測っていない | 目立たせないための意図した見た目。非活性のボタンはアクセシビリティの基準の対象外。**ほかの月の日付は押せるので対象外ではなく、未解決** | 見た目を見直すとき（まず実ブラウザで比を測る） |
| 網羅率のしきい値がない | `npm run coverage` で測るだけで、下がっても CI は赤くならない | 数字を目標にすると、中身の薄いテストが増えやすい。大事な所は、わざと壊して確かめた | 複数人で開発するとき |
| E2E が Chromium だけ | Firefox・Safari（WebKit）では確かめていない | 対象は PC の社内利用で、CI の時間が増える | 使うブラウザが Chrome・Edge 以外に広がるとき |
| 空白に見える一部の文字 | ハングルフィラー（U+3164・U+115F）や点字の空白（U+2800）は「見えない文字」に入らず、これだけの用件は空欄に見える | 普通の入力では出ない文字で、害は表示が空に見えるだけ | 利用者を信用できない環境で使うとき（画面と API の両方の定義に足す） |

**確認していないこと**: 同じ予約を「変更」と「キャンセル」で同時に操作すると、負けた側が分かりやすい文ではなく 500（「エラーが起きました」）になる可能性がある。コードを読んだ推測で、実際には試していない。
