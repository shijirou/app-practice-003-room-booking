## 2. 重複が、どんな操作でも重ならない

「わざと壊して」、二重（Java のチェック + DB の排他制約）が、それぞれ単独で効くかを確かめた。壊した変更は、そのあと元に戻した（`git status` が空）。

| 壊し方 | API テストの結果 | わかったこと |
|---|---|---|
| なし（元の状態） | 54 件、失敗 0 | 基準 |
| A: Java の重なりチェックを無効にした（DB の制約だけが守る） | 54 件、失敗 0 | 重なりは DB の排他制約だけでも止まり、409 になる（作成・変更とも） |
| B: DB の排他制約を無効にした（Java のチェックだけが守る） | 54 件中、失敗 2 件: 「同時に同じ枠を押しても予約は 1 件だけ」「DB の排他制約のテスト」 | 順番に押した重なりは Java で止まる。**同時に押されると Java だけではすり抜ける**。DB の制約が最後の砦で、テストがその崩れを検出する |

- 作成と変更のほかに、予約を書き込む道は無い（キャンセルは削除のみ。サンプルデータは起動時の Flyway だけ）。DB に直接入れても、排他制約が拒否する（`ReservationConstraintTest`）。
- E2E でも、同じ枠を同時に取ろうとすると 409 になり、画面にメッセージが出ることを確かめている。

**注意（確認していないこと）**
- 「同時の変更（PUT）」を並べて押す専用のテストは無い。A の結果（変更でも DB の制約が 409 にする）から、守られる仕組みは確認できたが、同時の変更そのものは実行していない。
