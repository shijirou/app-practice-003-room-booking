# セキュリティ確認の記録

公開リポジトリとして、またアプリ全体として安全かを確かめた記録。新しい確認は、日付つきで下に足す。

## 2026-11-24 公開前の確認（Issue #134）

### 1. Git の履歴（全コミット・全ブランチ）
| 確認 | 結果 |
|---|---|
| `.env`・鍵・証明書・ダンプなどのファイルが入ったことがあるか | 無し（`.env.example` だけ。中身は見本の文） |
| パスワード・トークン・API キーの値が入ったことがあるか | 無し（`${DB_PASSWORD}` などの参照のみ） |
| メールアドレス・電話番号などの個人情報 | 無し。コミットの名前・メールは GitHub の非公開用アドレス（noreply） |
| サンプルデータ | すべて架空（社員は「〇〇架空」） |
| GitHub の機能 | 秘密情報のスキャン（Secret scanning）と、プッシュ時の遮断（Push protection）は有効 |

### 2. 依存部品
| 確認 | 結果 |
|---|---|
| `npm audit`（開発用を含む・本番用のみ） | 0 件 |
| Java の部品 | Gradle には `npm audit` に当たる道具が標準では無いため、Dependabot（下の対応）で見張る |
| Action | コミットの SHA で固定済み。`permissions: contents read`・`persist-credentials: false` |
| 対応 | `.github/dependabot.yml` を追加（npm・gradle・github-actions・docker-compose を毎週） |

### 3. アプリ本体（API を起動して、攻撃的な入力を実際に送って確かめた）
| 試したこと | 結果 |
|---|---|
| SQL 風の文字（`' OR 1=1--`）を日付・社員番号に入れる | 400 で断られる。検索は JPA のパラメータ渡しで、文字をつなげた SQL は無い |
| 用件に `<img onerror=…>` を入れる | データとしては保存されるが、画面は React が文字として表示する（`dangerouslySetInnerHTML`・`innerHTML`・`eval` はコードに無い） |
| 他のサイトからの通信（CORS） | 許可の印が付かない（テストで固定） |
| `text/plain`・フォームでの POST（CSRF の典型） | 415 で断られる。JSON 以外を受けない |
| `/actuator`・`/h2-console` | 404（入れていない） |
| エラーの返事 | `{"message"}` だけ。スタックトレース・内部情報なし |
| 5MB の本文 | **指摘 1**: 読み込んでから 400（上限なし） → 修正 |
| 日付 `+999999999-01-01` | **指摘 2**: 500 エラー（日付の計算があふれる） → 修正 |
| セキュリティヘッダー | **指摘 3**: 1 つも付いていない → 修正 |
| 遠い未来（9999 年）の予約 | 「今日から 90 日先まで」と 400 |
| 長すぎる期間（0001〜9999 年）の検索 | 「62 日まで」と 400 |

### 4. 直したこと（このブランチ）
1. **本文の大きさに上限（10 KB）**: 超えたら読まずに 413。巨大な本文でメモリを使い切らせる攻撃（DoS の一種）を弱める
2. **日付の範囲（1900〜2200 年）**: 範囲外は 400。極端な年で 500 になる穴をふさぐ
3. **守りのヘッダー**: `X-Content-Type-Options`・`X-Frame-Options`・`Content-Security-Policy`・`Referrer-Policy`・`Cache-Control: no-store`
4. テスト 4 件（`SecurityTest`）。`SECURITY.md`（弱点の報告先）・`dependabot.yml`

### 5. 見送り・既知の制約（公開しても学習用として許容する理由）
| 項目 | 内容 | 方針 |
|---|---|---|
| 認証が無い | 送られた社員番号をそのまま信じる。他人の番号を送れば、その人の予約を変更・キャンセルできる | 要件の対象外（要件定義書）。README に明記。**インターネットに置かない** |
| 通信が HTTP | API は `127.0.0.1` のみ。暗号化なし | 公開する場合は HTTPS 終端（リバースプロキシ）が必須 |
| 回数制限なし | 短時間に大量の予約を作れる | 公開する場合は、リバースプロキシかゲートウェイで制限する |
| 本文の上限は Content-Length のみ | 分割転送（chunked）で送る場合は上限が効かない | 公開する場合は、プロキシ側で本文の大きさを制限する |
| DB ユーザーの権限 | 開発用の DB ユーザーは、Docker の既定でスーパーユーザー | 公開する場合は、実行用（読み書きのみ）と Flyway 用（表の変更）に分ける |
| 画面の CSP | 開発サーバー（Vite）は、動かすために inline スクリプトが要るので、画面側の CSP は付けていない | 公開する場合は、ビルドした画面を配るサーバーで CSP を付ける |
| 監査ログ | 誰がいつ何をしたかの記録なし | 認証が入るときに合わせて入れる |
| TRACE の 405・パス異常の 400 | Tomcat 標準の形の返事（`{"message"}` でない）。内部情報は無い | 見送り |

### 6. リポジトリの設定
2026-11-24 に、調べた結果にもとづいて 4 つを変更した（変更後の値は API で確認し、CI も再実行して通った）。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| main のルールセット | 削除禁止・強制プッシュ禁止・PR 必須・`check` 必須。例外（bypass）なし | そのまま |
| Actions の既定の権限 | read・PR の承認は不可 | そのまま |
| 外部の人の PR からのワークフロー | 初めての人だけ承認 | **外部の人はすべて承認** |
| Action の SHA 固定の強制 | 無効 | **有効** |
| Dependabot のセキュリティ更新 | 無効 | **有効** |
| 脆弱性の非公開報告 | 無効 | **有効** |
| Dependabot アラート・Secret scanning・Push protection | 有効 | そのまま |

### 7. これからの運用
- Dependabot の PR が来たら、CI（`check`）が通ることを確かめてからマージする。
- 脆弱性の報告が届いたら、「受け取りました」と返し、直したらその旨を添えて閉じる。通知を見逃さないよう、GitHub の通知設定（Watch → Custom → Security alerts）を確認しておく。
- 公開・実運用する場合は、「5. 見送り・既知の制約」の対応が先に必要。
